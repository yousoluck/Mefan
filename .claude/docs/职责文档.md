1. 二次开发场景总体概述

场景定义：在已有成熟项目上，增加新功能、修改现有功能行为、扩展 API 能力。
核心痛点：新代码破坏现有架构一致性、引入重复能力、修改公共 API 导致连锁故障。
与重构场景的关键区别：

维度 重构场景 二次开发场景
外部行为 必须 100% 一致 允许按需求变化
API 签名 绝对不可变 可增不可改，废弃需流程
测试重点 行为冷冻，Golden Master 回归测试 + 新功能集成测试
参考约束 原模块行为 项目中“最相似模块”的实现模式
并行开发 严格串行 允许无冲突的模块并行

核心约束：

1. 一致性 > 完美：新增代码的风格、模式、命名必须与项目现有代码一致。
2. API 兼容优先：公共 API 只能新增，不可修改签名。废弃需标记 @deprecated 并保留至少一个版本。
3. 复用优先：优先查找并使用项目已封装的工具函数、组件、服务，禁止引入功能重复的新依赖。
4. 最小变更：每次开发聚焦单一功能，禁止夹带无关重构、格式化、优化。
5. 冲突安全优先：并行开发时，以模块安全为最高原则，无法确定安全性时强制串行。
6. 债务显性化：所有技术债务必须记录、评估并纳入未来迭代计划。

4.1 阶段 1：需求澄清与现有系统分析（修订冲突检测）

参与 Agent：分析师 (主导)，PM (监督)

分析师职责（扩展）

1. 加载基线文件与图谱。
2. 与人类澄清功能目标、范围。
3. 系统关联与冲突拓扑分析（新增）：
   · 使用 graphify dependents 和 graphify similar 生成 “本次开发触达模块拓扑图”，标注所有潜在与其他任务交叉的模块。
   · 若存在交叉，标记为冲突风险，并预判冲突等级（核心模块冲突/边缘模块冲突）。
4. 提取命名约定、测试影响。
5. 输出 requirements/upgrade-YYYY-MM-DD-title.md，包含：
   · 冲突拓扑图摘要
   · 受影响模块清单及是否为冲突高发区
   · 可复用清单、命名约定、测试影响评估

PM 职责（修订）

1. 审查需求，特别关注冲突拓扑图，预判后续并行的可行性。
2. 若需求涉及已知正在开发的其他任务模块，暂时标记为“待冲突裁决”，在阶段 3 集中处理。

4.2 阶段 2：架构设计与测试策略（新增设计冲突处理）

参与 Agent：架构师 (主导)，QA 工程师 (辅助)

架构师职责（新增设计冲突处理）

1. 设计技术方案，输出 ADR，必须包含：
   · 一致性合规声明：明确指出设计方案“遵循已有模式”或“有意突破已有模式”。
   · 若为突破：必须提供详细理由，并附带 “一致性基线修正提案”（草稿）。
2. QA 工程师同步输出测试计划。

设计冲突处理流程（新增）

· 架构师识别到的设计冲突，由 PM 审核。若 PM 认为理由充分，提交 人类决策。
· 若人类批准突破，基线修正提案转入 evolution-proposals/，在阶段 6 正式评估是否更新基线。

4.3 阶段 3：迭代计划与任务排期（冲突裁决与并行规则）

参与 Agent：PM (主导)，分析师 (拆解)

PM 职责（重大修订）

1. 拆解任务后，执行并行冲突裁决：
   · 比对每个任务的“触达模块拓扑图”，计算交集。
   · 强制串行条件：任务触及同一核心模块（认证、支付、数据一致性层），即使无直接依赖也强制串行。
   · 可并行条件：任务仅触及边缘模块或独立新增模块，且冲突分析无副作用。
   · 不确定性原则：当无法 100% 确定无冲突时，默认串行。
2. 将裁决结果写入 iterations/upgrade-sprint-YYYY-MM-DD.md，并标注“并行/串行”理由。
3. 设置 WIP 限制，确保并行任务数 ≤ 安全并行数。
4. 为每个任务设定进度警戒线（如完成度 50% 时进度应过半）。

冲突升级（新增）

· 若 PM 无法裁决（如影响面涉及多团队或复杂业务），生成《冲突裁决申请》提交人类决策。

4.4 阶段 4：迭代实现（澄清 Hook 与守护者边界，补充异常处理）

参与 Agent：开发者 (主导)，守护者 (审查)，PM (监控)

开发者职责

1. 按 TDD 流程实现，遵循一致性、复用规则。
2. 每次代码保存后，Hook 自动执行（详见下方）。
3. 任务完成后，生成 task-summary/<task-id>.md，并记录所有技术债务。

Hook 与守护者边界（新增澄清）

· Hook 是自动化脚本，不是 Agent。它在 PostToolUse 时被触发，执行固定检查（命名、风格、diff 范围、API 兼容性），产出 violations.json。
· 守护者 Agent 拥有推理能力，在任务完成后被激活。它：
  · 读取 violations.json
  · 执行深度 Code Review（语义、安全、性能、设计一致性）
  · 做出最终决策（通过/有条件通过/驳回）
· 两者关系：Hook 是传感器的原始信号，守护者是分析信号并做出裁决的大脑。Hook 失败会阻止代码提交，但最终放行需守护者批准。

异常处理：连续 Hook 拦截（新增）

· 第 1 次拦截：开发者自行修复。
· 第 2 次拦截：开发者必须写 interception-analysis.md 说明根因。
· 第 3 次拦截：暂停任务，PM 介入，可能回溯至阶段 2 调整设计，或通知人类介入。

PM 职责（新增进度监控与滞后处理）

· 监控任务进度，当任务触及阶段 3 设定的警戒线时：
  · 自动生成提案：缩小范围/延长期限（需人类批准）/增加资源。
  · 默认建议缩小范围，移出低优先级任务至下个迭代。

4.5 阶段 5：质量测试与门禁（补充 P0 异常处理、人工测试闭环）

参与 Agent：QA (主导)，开发者 (修Bug)，守护者 (终审)，PM (决策)

人工测试与 P0 Bug 处理（新增）

· QA 生成 manual-test-guide.md，包含人工测试用例与环境搭建步骤。
· 人工测试发现的 Bug 按 bug-log/manual-*.md 模板提交，由 PM 审核定级。
· P0 Bug 处理优先级最高：
  · PM 宣布暂停当前迭代所有其他开发任务。
  · 开发者立即修复，可突破最小变更约束但需完整记录。
  · 修复后重新走阶段 5 门禁，通过后 PM 宣布恢复其他任务。

守护者职责

· 执行门禁，包含自动化扫描与人工 Bug 状态检查。

进度滞后处理（延续阶段 4）

· 若因大量 Bug 导致测试周期严重超期，PM 启动“滞后处理”流程，与阶段 4 的滞后应对机制一致。

4.6 阶段 6：迭代总结与进化（技术债务管理正式纳入）

参与 Agent：PM (主导总结)，进化教练 (分析)，守护者 (验证)

PM 职责（新增技术债务管理）

1. 撰写 iteration-retrospective.md，增加 “技术债务评估” 固定章节：
   · 当前累积债务清单（从各 task-summary 和 bug-log 汇总）
   · 债务偿还成本估算（工时/风险）
   · 对下一迭代的影响判断
   · 若某模块债务 ≥ 3 项未偿还，强制在下个迭代计划中优先安排偿还任务（至少偿还 50% 再开发新功能）
2. 启动进化教练流程，分析缺陷模式、Hook 拦截日志、债务趋势。

进化监督（新增）

· 三权分立：进化教练提案 → PM 审批 → 守护者验证（在下一迭代中实验性运行，检查冲突与退化）
· 框架版本管理：所有框架文件变更需通过 Git 管理，PM 更新 HARNESS_VERSION.md。

5. 全局异常处理机制（新增独立章节）

为应对各阶段非正常情况，特设立以下标准处理流程，写入 knowledge/global/exception-handling.md，所有 Agent 必须遵守。

异常场景 触发条件 处理流程 责任人
连续 Hook 拦截 同一任务 Hook 拦截 ≥ 3 次 暂停任务 → PM 评估是否回溯设计 → 人类介入 开发者、PM
设计冲突 架构方案需突破一致性基线 架构师提交理由+修正提案 → PM+人类裁决 架构师、PM
P0 人工 Bug 人工测试发现 P0 缺陷 暂停迭代其他任务 → 开发者修复 → 重新测试 → 恢复 PM、开发者
进度严重滞后 任务进度触及警戒线 PM 自动生成提案（缩小范围/延长期/加资源）→ 人类决策 PM
模块冲突无法裁决 PM 无法判定串并行安全 生成《冲突裁决申请》→ 提交人类决策 PM
