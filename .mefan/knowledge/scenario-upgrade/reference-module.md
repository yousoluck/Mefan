# Reference Module（参考模块）
- type: guideline
- severity: warning

## 目的

为二次开发场景指定权威的参考模块，作为代码风格、架构模式、命名约定的蓝本。

## 核心原则

1. **单一权威来源**：每个技术栈/模块类型，只指定一个权威参考模块
2. **优先复用**：新代码实现前，必须先参考指定模块的写法
3. **明确偏差**：如需突破参考模块的模式，必须在 ADR 中说明理由

## 使用场景

| 阶段 | 使用时机 |
|------|----------|
| **阶段2 架构设计** | 架构师选择参考模块，产出 consistency-baseline.md |
| **阶段4 迭代实现** | 开发者实现新功能前，参考指定模块的代码模式 |

## 指定方法

### 1. 识别参考模块

在系统关联分析后，分析师和架构师共同确定：

- 与新功能最相似的已有模块
- 该模块在一致性和复用性上表现良好
- 无已知技术债务或严重缺陷

### 2. 记录参考模块

在 `consistency-baseline.md` 中记录：

```markdown
## 参考模块清单

| 模块类型 | 参考模块路径 | 理由 | 适用场景 |
|----------|-------------|------|----------|
| API设计 | `src/api/user.py` | 风格一致，结构清晰 | 新增REST API |
| 数据模型 | `src/models/order.py` | 字段定义规范 | 新增数据模型 |
| 服务层 | `src/services/payment.py` | 事务处理模式 | 新增业务逻辑 |
```

### 3. 使用参考模块

开发者在实现时应：

1. 阅读参考模块的完整实现（不只是接口）
2. 遵循相同的：
   - 命名约定（变量、函数、类、文件）
   - 目录结构
   - 错误处理模式
   - 注释风格
3. 如有疑问，先参考再实现

## 偏差处理

如果新需求与参考模块模式不匹配，需要突破时：

1. 在 ADR 中明确标注"突破参考模块：{模块名}"
2. 说明突破理由和替代方案
3. 经 PM 和人类批准后，更新 consistency-baseline.md

## 适用阶段

- 阶段2（架构设计）：架构师指定参考模块
- 阶段4（迭代实现）：开发者遵循参考模块实现
