# Evolution Process（框架进化流程）
- type: constraint
- severity: error

## 目的

规范进化提案的生成、实验验证、审批、合并流程，确保框架有序演进而不引入退化。

## 进化提案来源

| 来源 | 触发条件 | 提出者 |
|------|----------|--------|
| 迭代复盘 | 阶段6发现缺陷模式或改进机会 | 进化教练 |
| Hook拦截趋势 | 连续多次拦截同类问题 | PM |
| 技术债务积累 | 某模块债务 ≥ 3 项 | PM |
| 人类建议 | 框架使用者提出改进建议 | 人类 |

## 三权分立机制

进化流程涉及三个角色的分工与制衡：

```
进化教练提案 → PM审批 → 守护者验证
```

| 角色 | 职责 | 产出物 |
|------|------|--------|
| **进化教练** | 分析缺陷模式、生成进化提案 | `evolution-proposal.md` |
| **PM** | 审批提案、决策是否实验 | 批准/驳回决策 |
| **守护者** | 在下一迭代验证实验效果 | 验证报告 |

## 进化提案模板

使用 `templates/evolution-proposal-template.md`，包含：

```markdown
# Evolution Proposal: {提案名称}

## 提案触发原因
{为什么会提出这个提案}

## 当前问题分析
{问题根因分析}

## 提案方案（草案）
{具体的改进方案}

## 预期效果
{改进后的预期效果}

## 潜在风险
{可能引入的新问题}

## 实验计划
{如何在下一迭代中验证}

## 审批状态
- [ ] PM审批：待审批/批准/驳回
- [ ] 守护者验证：待验证/通过/不通过
```

## 实验与验证流程

### 阶段1：提案生成（阶段6）

1. 进化教练分析 iteration-retrospective.md 中的缺陷模式
2. 如果发现值得改进的点，生成 `evolution-proposal.md`
3. 提案写入 `.mefan/evolution-proposals/`

### 阶段2：PM审批

PM收到提案后：
1. 评估提案的合理性和优先级
2. 如果批准，标记为"实验性"并指定实验迭代
3. 如果驳回，说明驳回理由

### 阶段3：实验迭代（正常迭代）

在实验迭代中：
1. 按提案方案实现改进
2. 守护者监控实验效果
3. 记录实验数据（Hook拦截次数、缺陷率等）

### 阶段4：验证与决策

守护者在实验迭代结束后：
1. 输出验证报告
2. 如果实验成功 → 更新到正式Rule/Skill
3. 如果实验失败 → 撤销实验，保留经验教训

## 合并决策

| 实验结果 | 处理方式 |
|----------|----------|
| 成功 | 正式合并到框架，更新相关Rule/Skill，递增版本 |
| 失败 | 撤销实验，更新提案状态为"不采纳"，记录教训 |
| 需要调整 | 返回提案阶段，重新设计方案 |

## 框架版本管理

进化提案被采纳后：
1. PM更新 `HARNESS_VERSION.md`（至少递增PATCH）
2. 变更内容写入 `CHANGELOG.md`
3. 相关文件（Rule/Skill/Template）更新到新位置

## 禁止事项

1. **禁止未经实验直接合并**：所有框架变更必须经过实验验证
2. **禁止跨迭代携带未验证提案**：提案有效期为1个迭代
3. **禁止强行推动有争议的提案**：如PM和守护者意见不一致，必须提交人类决策

## 适用阶段

- 阶段6（迭代总结与进化）：进化教练生成提案
- 下一迭代（实验与验证）：守护者验证实验效果
