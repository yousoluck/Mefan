# Manual Test Bug Handling（人工测试Bug处理）
- type: constraint
- severity: error

## 目的

规范人工测试发现的Bug提交、分类、修复、验证的完整闭环流程，确保P0缺陷得到最高优先级处理。

## Bug分类标准

| 严重度 | 定义 | 处理时效 |
|--------|------|----------|
| **P0** | 系统崩溃、数据丢失、安全漏洞、核心功能完全不可用 | 立即处理，暂停其他任务 |
| **P1** | 重要功能失效，但有临时 workaround | 24小时内修复 |
| **P2** | 功能部分失效，影响业务流程 | 下一个迭代修复 |
| **P3** | 边界情况、UI问题、体验优化 | 规划中修复 |

## Bug提交流程

### 1. 发现Bug（QA/开发者/人类）

发现Bug后，提交到 `iterations/{sprint-name}/bug-log/manual-YYYY-MM-DD.md`：

```markdown
## Bug记录

| 字段 | 内容 |
|------|------|
| Bug ID | BUG-YYYY-MM-DD-NNN |
| 提交人 | {姓名} |
| 发现时间 | {时间戳} |
| 严重度 | P0/P1/P2/P3 |
| 模块 | {受影响的模块} |
| 标题 | {简短描述} |
| 复现步骤 | 1. 2. 3. |
| 预期行为 | {应该怎样} |
| 实际行为 | {实际怎样} |
| 截图/日志 | {附件路径} |
```

### 2. PM定级

PM收到Bug提交后：
- 审核Bug描述的完整性和准确性
- 确定严重度（P0立即通知PM）
- 分配给合适的开发者修复

### 3. P0处理流程（最高优先级）

当发现P0 Bug时：

1. **立即暂停**：PM宣布暂停当前迭代所有其他开发任务
2. **通知开发者**：指定开发者立即投入P0修复
3. **突破约束**：允许突破最小变更约束，但需完整记录变更
4. **临时方案**：如果可能，提供临时 workaround 让系统可以继续运行
5. **修复验证**：修复后重新走阶段5门禁（回归测试 + 集成测试）
6. **恢复迭代**：门禁通过后，PM宣布恢复其他任务

### 4. P1-P3处理流程

| 阶段 | 操作 | 负责人 |
|------|------|--------|
| 提交 | 创建bug-log/manual-YYYY-MM-DD.md | QA |
| 定级 | PM确定严重度 | PM |
| 修复 | 开发者修复 | 开发者 |
| 验证 | 回归测试确认 | QA |
| 关闭 | 更新Bug状态为Done | QA |

## 与自动化测试的关系

- **自动化测试发现Bug**：记录到 `bug-log/auto-YYYY-MM-DD.md`
- **人工测试发现Bug**：记录到 `bug-log/manual-YYYY-MM-DD.md`
- 两者都汇总到阶段5的质量报告中

## 异常场景

### 场景1：多个P0同时发现

- 按发现时间顺序处理
- PM可以调度多个开发者并行修复不同P0
- 如果P0数量 > 3，PM需要上报人类决策

### 场景2：P0修复后引入新Bug

- 将新Bug作为新的P0处理
- 分析是否需要回滚
- PM决定是否继续修复或回滚

### 场景3：Bug无法在时效内修复

- P0：立即上报PM和人类
- P1：PM决定是否延期或缩小范围

## 适用阶段

- 阶段5（质量测试与门禁）：Bug提交、分类、修复、验证
