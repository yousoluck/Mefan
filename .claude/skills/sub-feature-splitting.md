# Sub-feature 拆分方法论
- 触发条件：BA 完成 User Story 拆分后，将每个 US 拆分为 Sub-feature
- 适用 Agent：BA

---

## 拆分原则

### 最小化粒度原则

| 原则 | 说明 | 目标 |
|------|------|------|
| **独立开发** | 每个 SF 可独立开发、测试、部署 | 2-4 小时工作量 |
| **单一职责** | 每个 SF 只做一件事 | 高内聚 |
| **清晰边界** | SF 之间通过 API 或事件交互 | 低耦合 |
| **可独立测试** | 每个 SF 有明确的验收标准 | 测试覆盖 |

---

## 拆分维度

### 1. 按技术层次拆分

| 维度 | 说明 | 示例 |
|------|------|------|
| **前端 (frontend)** | UI 组件、页面交互 | 订单列表组件、下单按钮 |
| **后端逻辑 (backend)** | 业务逻辑、服务处理 | 库存检查逻辑、优惠计算 |
| **API 接口 (api)** | REST/GraphQL 接口定义 | 创建订单 API、查询订单 API |
| **数据访问 (db)** | 数据库操作、缓存 | 订单表写入、Redis 缓存 |
| **基础设施 (infra)** | 配置、部署、环境 | Nginx 配置、K8s 部署 |

### 2. 按业务能力拆分

| 维度 | 说明 | 示例 |
|------|------|------|
| **读写分离** | 查询 vs 写入 | 订单查询 vs 订单创建 |
| **权限分离** | 不同角色不同操作 | Admin vs User |
| **模块分离** | 不同业务域 | Order vs Payment |

### 3. 按功能复杂度拆分

| 维度 | 说明 | 适用场景 |
|------|------|---------|
| **核心功能** | 主要业务流程 | 用户下单、支付 |
| **边界处理** | 错误、异常、边界值 | 输入校验、超时处理 |
| **辅助功能** | 次要但必要 | 日志记录、监控埋点 |

## 拆分步骤

### 步骤 1：分析 US 的技术层次

**目的**：确定这个 US 需要哪些技术层次的 SF

**方法**：
1. 阅读 US 的描述和 AC
2. 回答：实现这个 US 需要哪些层次的代码？

**输出**：

| SF 编号 | 技术层次 | 说明 |
|---------|---------|------|
| SF-001-1 | frontend | 订单列表页面组件 |
| SF-001-2 | api | 订单查询 API |
| SF-001-3 | backend | 订单服务逻辑 |
| SF-001-4 | db | 订单表读写 |

---

### 步骤 2：识别 SF 的功能边界

**目的**：确保每个 SF 的功能单一、边界清晰

**检查问题**：
- 这个 SF 做什么？
- 这个 SF 不做什么？
- 它与其他 SF 的交互点是什么？

**输出**：

| SF ID | 功能名称 | 功能范围内 | 功能范围外 |
|-------|---------|-----------|-----------|
| SF-001-1 | 订单列表组件 | 显示订单、翻页、筛选 | 下单、支付 |
| SF-001-2 | 订单查询 API | 查询订单、返回数据 | 修改、删除 |

---

### 步骤 3：确定 SF 的接口

**目的**：明确 SF 与其他 SF 的交互方式

**API 定义**：

| SF | 接口类型 | 路径/方法 | 参数 | 返回值 |
|----|---------|---------|------|--------|
| SF-001-2 | REST | GET /api/orders | page, size, status | OrderList |
| SF-001-3 | 内部调用 | OrderService.getOrders() | filter: OrderFilter | List<Order> |

**事件定义**（如有）：

| SF | 事件 | 触发条件 | 订阅方 |
|----|------|---------|--------|
| SF-001-4 | order.created | 订单创建成功 | 库存服务、通知服务 |

---

### 步骤 4：编写 SF 的验收标准

**目的**：每个 SF 必须有明确的、可测试的验收标准

**格式**：Gherkin 格式

| AC ID | 场景 | Given | When | Then |
|-------|------|-------|------|------|
| SF-001-2-AC1 | 查询订单 | 用户已登录 | 调用 GET /api/orders | 返回订单列表 |
| SF-001-2-AC2 | 分页 | 页码为 2，每页 10 条 | 调用 GET /api/orders?page=2 | 返回第 11-20 条订单 |
| SF-001-2-AC3 | 筛选 | status=paid | 调用 GET /api/orders?status=paid | 只返回已支付订单 |

---

### 步骤 5：标注 SF 的依赖关系

**目的**：明确 SF 与其他 US/SF 的依赖

**依赖类型**：

| 类型 | 依赖项 | 说明 |
|------|--------|------|
| 前置依赖 SF | SF-003-2 | 必须先完成用户认证 |
| 依赖外部服务 | PaymentGateway | 调用第三方支付 |
| 被依赖关系 | SF-001-5 | 订单查询依赖本 SF |

---

### 步骤 6：非功能性需求提取

**目的**：识别每个 SF 的非功能性需求

| 类型 | 需求描述 | 量化指标 | SF 归属 |
|------|---------|---------|---------|
| **性能** | API 响应时间 | < 200ms | SF-001-2 |
| **可用性** | 接口可用性 | 99.9% | SF-001-2 |
| **可观测性** | 埋点事件 | order.query | SF-001-2 |
| **安全性** | 权限校验 | 必须登录 | SF-001-2 |
| **操作需求** | 大文件支持 | 订单附件 < 10MB | SF-001-3 |

---

### 步骤 7：风险评估

**目的**：提前识别 SF 实现风险

| 风险类型 | 描述 | 影响 SF | 应对方案 |
|---------|------|---------|---------|
| 技术难度 | 复杂查询优化 | SF-001-2 | 预留 SQL 优化时间 |
| 外部依赖 | 第三方支付不稳定 | SF-001-4 | 实现降级策略 |
| 数据一致性 | 分布式事务 | SF-001-3, SF-001-4 | 使用消息队列 |

---

### 步骤 8：判断拆分完成

**检查清单**：

| 检查项 | 标准 | 通过 |
|--------|------|------|
| 粒度最小化 | 2-4 小时工作量 | ✅/❌ |
| 单一职责 | 只做一件事 | ✅/❌ |
| 清晰边界 | 与其他 SF 无重叠 | ✅/❌ |
| 接口明确 | API/事件已定义 | ✅/❌ |
| 可独立测试 | 有 AC | ✅/❌ |
| 依赖标注 | 前置/被依赖已标注 | ✅/❌ |
| 非功能需求 | 已提取性能、安全等 | ✅/❌ |
| 风险评估 | 已识别风险和方案 | ✅/❌ |

## SF 类型指南

### Frontend SF

| 类型 | 说明 | 产出物 |
|------|------|--------|
| 页面组件 | 完整页面或区块 | React/Vue 组件 |
| 交互逻辑 | 用户操作处理 | 事件处理器 |
| 状态管理 | 前端数据状态 | Store/State |

### Backend SF

| 类型 | 说明 | 产出物 |
|------|------|--------|
| 业务逻辑 | 核心业务处理 | Service 类 |
| 数据处理 | 数据转换/计算 | Helper/Util 类 |
| 业务规则 | 规则引擎 | Rule 引擎配置 |

### API SF

| 类型 | 说明 | 产出物 |
|------|------|--------|
| 接口定义 | 请求/响应格式 | OpenAPI/Swagger |
| 参数校验 | 输入验证 | Validator |
| 错误处理 | 异常响应 | Error Handler |

### DB SF

| 类型 | 说明 | 产出物 |
|------|------|--------|
| 数据模型 | 表结构设计 | Entity/DDL |
| 数据访问 | CRUD 操作 | Repository |
| 数据迁移 | 数据转换脚本 | Migration |

### Infra SF

| 类型 | 说明 | 产出物 |
|------|------|--------|
| 配置管理 | 环境配置 | Config 文件 |
| 部署脚本 | 部署自动化 | CI/CD Pipeline |
| 监控埋点 | 可观测性 | Metrics/Logs |

## 常见问题

### Q1：SF 之间有循环依赖怎么办？

**解决**：
1. 识别共同的数据对象
2. 将共享逻辑提取到新的 SF
3. 考虑合并相关 SF

### Q2：SF 太细碎了怎么办？

**问题**：几十个小 SF，维护成本高

**解决**：
1. 按模块分组管理
2. 合并高度相关的 SF
3. 保持粒度在合理范围（1-5 个 SF/US）

### Q3：如何处理跨 US 的公共 SF？

**问题**：多个 US 都需要的公共功能

**解决**：
1. 识别公共功能（如认证、日志）
2. 单独创建基础设施类 SF
3. 在每个 US 中引用该公共 SF
